1. The big picture

1.1 The problem this solves

Hand-written UI automation is slow to build and breaks easily. Most of the effort goes into repetitive work: reading the story, listing test cases, finding locators for every field, writing page objects and keeping them up to date when the screen changes. This framework hands that repetitive work to an AI coding assistant (Claude), inside a fixed structure, so that:

  • every module follows the same path: requirement → test cases → automated tests → report;
  • QA engineers review and decide; Claude drafts, writes code, runs tests and fixes automation problems;
  • one shared framework serves every application in the company, web and mobile;
  • each test is traceable: Jira story → test-case ID → test → result in the report.

1.2 What is in the box

PieceWhat it does
PlaywrightDrives real browsers (Chrome, Safari engine) and runs the tests. Also emulates phones for mobile web.
Appium (via WebdriverIO)Drives native Android and iOS apps on emulators or devices.

1.3 Who does what

2. How Playwright + Claude AI automation works

This section explains the general idea, independent of our framework. Once you understand these five building blocks, the rest of the guide is detail.

2.1 Playwright: the test engine

Playwright is an open-source library from Microsoft that controls a browser through code. A Playwright test is a TypeScript function that opens pages, interacts with them and checks the result:

test('valid user can log in', async ({ page }) => {
  await page.goto('https://www.saucedemo.com');
  await page.getByTestId('username').fill('standard_user');
  await page.getByTestId('password').fill('secret_sauce');
  await page.getByTestId('login-button').click();
  await expect(page).toHaveURL(/inventory/);        // web-first assertion: retries until true or timeout
});

The key ideas:

  • Locators describe how to find an element: by test ID, by accessible role and name, by label, by text. Stable locators are the single biggest factor in stable tests.
  • Auto-waiting: actions wait until the element is visible, enabled and stable, so tests need no sleep.
  • Web-first assertions: expect(...) retries until the condition is true or the timeout expires.
  • Projects: the same tests run on several browsers and devices (desktop Chrome, Pixel 7, iPhone 15).
  • Fixtures: reusable setup handed to each test (a page, a logged-in session, an API client).
  • Trace, screenshots and video are recorded on failure, so you can replay exactly what happened.

2.2 Appium: the same idea for native apps

Browsers can't run native Android/iOS apps, so for those we use Appium, a server that controls apps on an emulator, simulator or real device. We talk to it with WebdriverIO, but the framework hides this: mobile tests are written exactly like web tests (models, screens, act / verify), and Playwright's runner still runs them and produces the same report.

2.3 Claude Code: the AI that writes and runs the tests

Claude Code is Anthropic's AI coding assistant. In VS Code it works in a side panel and, unlike a chat bot, it can read and edit files in the project and run terminal commands (with your permission). That makes it an agent: you give it a goal ("automate these test cases"), and it reads the inputs, writes the code, runs the tests, reads the failures and fixes them, in a loop, until the goal is reached.

Two project files steer its behaviour:

  • CLAUDE.md (repository root): the project rules, read automatically at the start of every conversation. Folder layout, naming, "locators only in models", "no sleeps", how to mark a known bug. This is why Claude's code looks like the rest of the framework.
  • Slash commands (.claude/commands/*.md): saved, step-by-step instructions you start by typing /qa-automate <file>. Each step of our process has one, so everybody gets the same result.

2.4 MCP and the Playwright MCP: letting Claude see the application

MCP (Model Context Protocol) is an open standard for giving an AI assistant extra tools. The Playwright MCP server gives Claude a real browser it can drive while it works: open a URL, read the page structure (an accessibility snapshot), click, type, run JavaScript in the page, take screenshots.

Why it matters: without it, Claude would have to guess locators and message texts from the requirement. With it, Claude logs in to the QA environment with a test account, opens the screen, lists the real test IDs, triggers each validation error to read its exact text, and only then writes the model. When a test fails, it can replay the steps in the browser to tell an automation problem from an application bug.

The server is configured for this project in .mcp.json, and .claude/settings.json pre-approves its tools. Native mobile apps can't be opened through it; for those, test IDs come from the module MD file or Appium Inspector.

2.5 How the pieces work together

Important: the AI writes the tests, it doesn't run them in production The generated tests are ordinary TypeScript files committed to the repository. Running them, locally or in CI, needs no AI at all. Claude is only involved when tests are created, changed or investigated.

2.6 Where AI helps, and where humans must decide

Claude is good at

  • Turning a structured requirement into a complete list of positive, negative and boundary cases
  • Finding stable locators on a real page
  • Writing consistent model / page / data / spec code
  • Running tests, reading errors, fixing locators and waits
  • Spotting gaps in a requirement ("no error text given for...")

QA must decide

  • Whether the test cases are right and complete (review step)
  • What the expected result is: the requirement wins, never the current app behaviour
  • Whether a failure is a real bug, and raising it in Jira
  • Merging generated code (review it like any pull request)
  • Signing off a module
Never let a test be "fixed" by weakening the check If the application shows the wrong message, the test must keep expecting the right one. Confirmed bugs are marked with knownBug('JIRA-KEY', 'summary') (section 11.3), not by changing the assertion to match the bug. The commands are written to enforce this; reviewers should check it too.

cd "Automation Framework"

# 2. install dependencies and browsers
npm install

copy .env.example .env                                  # macOS/Linux: cp

The root .env chooses the app and environment:

JIRA_BASE_URL=https://yourcompany.atlassian.net   # turns Jira keys in the report into links

Each app's own apps/<app>/.env holds its QA URLs, test accounts per role, API token and mobile app builds. Ask the QA lead for the values of real projects. They contain QA test accounts only, never production credentials.

3.3 First run

npx tsc --noEmit             # type check: should print nothing
npm run test:web             # sample app tests on desktop Chrome (logs in first, then runs the specs)
npm run report               # builds and opens the Allure report in your browser

If you see green tests and a report grouped under Authentication and Shopping, the framework works.

3.4 Set up Claude Code and the browser tool

  1. Install the Claude Code extension in VS Code and sign in with your Claude account.
  2. Open the project folder (the one with CLAUDE.md) and open the Claude panel.
  3. The project's .mcp.json declares the playwright MCP server. When Claude asks to enable it, approve it.
  4. Type /mcp in the Claude panel: playwright should be listed as connected.
  5. Type / and check that qa-testcases, qa-automate, qa-fix and qa-update appear.
Playwright MCP not listed or not connecting? Add it for your user once, then reload VS Code and start a new Claude conversation: 
claude mcp add playwright --scope user -- cmd /c npx -y @playwright/mcp@latest --isolated --output-dir=.playwright-mcp
On macOS/Linux leave out cmd /c (the same applies to .mcp.json, which is written for Windows). The first start downloads the package and can time out; retry once it has finished.

3.5 Try Claude on the sample app

Ask Claude, in plain words, to explain or run something. Good first prompts:

  • "Explain how apps/saucedemo/tests/web/login/login.spec.ts finds its test case in the report."
  • "Run the products tests on web-chrome and summarise the result."
  • "Open saucedemo.com in the browser and list the data-test IDs on the login page." (uses the MCP browser)

4. How the framework is built

4.1 Folder layout

  models/                field.types.ts: Field, WebLocator, MobileLocator, FormData, defineWebFields
  web/                   BasePage, WebActions (act), WebAssertions (verify), locator resolver
  mobile/                BaseScreen, MobileActions, MobileAssertions, Appium driver + capabilities
  api/                   ApiClient (REST for setup / cleanup)

  fixtures/              core `test`: role, platform, api, cleanup, driver, report (automatic)
  report/                Allure enrichment: test case per test, failure cause, bug report attachment
  utils/                 step(), storyInfo() / knownBug(), cleanup, random data

  app.config.ts          platforms, web base URL, test-id attribute, login roles + login steps
  fixtures.ts            adds this app's pages/screens to the core test; specs import from here
  .env                   URLs, accounts, builds for this app (not committed)
  requirements/          module MD files (+ .baseline/ = versions QA has processed)
  test-cases/            reviewed test cases (*.testcases.md)
  sprints/               sprint trackers + developer MDs as received (from-dev/<date>/)
  models/web|mobile      field models       pages/   screens/    page and screen objects
  data/                  typed test data    tests/web|mobile      specs

Imports use two aliases: @core/... for src/ and @apps/<app>/... for app code.

4.2 How settings are resolved

APP picks the folder under apps/. Then settings are loaded, first value wins:

  1. real environment variables (CI secrets, or set on the command line)
  2. apps/<app>/.env.<TEST_ENV>, e.g. .env.staging
  3. apps/<app>/.env
  4. root .env (shared values such as JIRA_BASE_URL)

BASE_URL and TEST_ID_ATTRIBUTE in an env file override the defaults in app.config.ts, so one app can be tested against QA, staging, etc. In code, read settings only through getEnv('NAME') / requireEnv('NAME') from @core/config/env.

4.3 Platforms become Playwright projects

platforms in the app's app.config.ts decides which test projects exist:

PlatformProject(s)RunsTests folder
webweb-chromeDesktop Chrometests/web
mobile-webmobile-web-android, mobile-web-iosResponsive web on Pixel 7 (Chromium) and iPhone 15 (WebKit)

Web projects depend on a setup project that logs in every role once and saves the sessions in .auth/<app>/<role>.json. Each test then starts already logged in, which keeps tests fast.

4.4 The four layers of every module

Each module is built from four small files. Examples are from the sample app apps/saucedemo.

1Model: what is on the screen (the only place locators live)

// apps/saucedemo/models/web/login.model.ts
export const LoginFields = defineWebFields({
  username: { label: 'Username', type: 'text', locator: { testId: 'username' },
              rules: { required: true, messages: { required: 'Epic sadface: Username is required' } } },
  password: { label: 'Password', type: 'password', locator: { testId: 'password' } },
  loginButton: { label: 'Login button', type: 'button', locator: { testId: 'login-button' } },
  errorMessage: { label: 'Error message', type: 'label', locator: { testId: 'error' } },
});
export const LoginMessages = { invalidCredentials: 'Epic sadface: Username and password do not match ...' } as const;
export type LoginData = FormData<typeof LoginFields>;   // { username?: string; password?: string } (derived)

The label is what appears in the report (Fill "Username" with "standard_user"). The type tells the framework how to fill the field. The data type is derived from the model, so data and model can't drift apart.

2Page (web) or screen (mobile): business actions

// apps/saucedemo/pages/LoginPage.ts
export class LoginPage extends BasePage {
  readonly path = '/';
  readonly fields = LoginFields;

  async login(data: LoginData) {
    await this.act.fillForm(this.fields, data);      // fills each field present in data, by its type
    await this.act.click(this.fields.loginButton);
  }
  async expectError(message: string) {
    await this.verify.text(this.fields.errorMessage, message);
  }
}

Pages use only this.act.* (actions) and this.verify.* (assertions). Both write a readable report step for every call. Each page/screen is registered once in apps/<app>/fixtures.ts so tests can ask for it by name.

3Data: typed by the model

// apps/saucedemo/data/web/login.data.ts
export const validUser: LoginData = { username: getEnv('WEB_USERNAME'), password: getEnv('WEB_PASSWORD') };
export const invalidLoginCases = [
  { id: 'TC-LOGIN-04', title: 'Empty username shows required error',
    data: { password: getEnv('WEB_PASSWORD') },                 // username left out = left empty
    error: LoginFields.username.rules.messages.required },
  // ...
];

4Spec: reads like the test case

// apps/saucedemo/tests/web/login/login.spec.ts
import { test } from '@apps/saucedemo/fixtures';               // never from '@playwright/test'

test.use({ role: null });                                        // login tests start logged out

test.describe('Login', () => {
  test.beforeEach(async ({ loginPage }) => {
    await storyInfo({ epic: 'Authentication', feature: 'Login', story: 'SCRUM-101 User can log in',
                      jira: 'SCRUM-101', severity: 'critical' });
    await loginPage.open();
  });

  test('TC-LOGIN-01 | Valid user is taken to the Products page', { tag: ['@smoke', '@TC-LOGIN-01'] },
    async ({ loginPage, inventoryPage }) => {
      await loginPage.login(validUser);
      await inventoryPage.expectLoaded();
    });

  for (const tc of invalidLoginCases) {                            // data-driven negative cases
    test(`${tc.id} | ${tc.title}`, { tag: ['@regression', `@${tc.id}`] }, async ({ loginPage }) => {
      await loginPage.login(tc.data);
      await loginPage.expectError(tc.error);
    });
  }
});

One test per test-case ID, titled <ID> | <Title>. The report uses the ID in the title to find the test case in the *.testcases.md file and show its steps and expected result next to the result.

5. Walkthrough: automating a module with Claude

This is the day-to-day workflow. The example automates a "registration" module of an app called shop; replace the names with yours.

Step 0: check which app you are on

APP in the root .env must be the app you work on (here APP=shop). Claude also derives the app from the file path you give it.

Step 1: put the requirement in place

Copy templates/requirement.md to apps/shop/requirements/web/SCRUM-123-registration.md and fill it in (or paste the developer's notes / Jira story). The more exact it is (field rules, exact error texts, test IDs), the better the tests. The companion guide lists what a complete file contains and has a full example.

Step 2: generate test cases

/qa-testcases apps/shop/requirements/web/SCRUM-123-registration.md

Claude reads the requirement (and may open the page in the MCP browser to confirm fields) and writes apps/shop/test-cases/web/registration.testcases.md in the format of templates/testcases.md: IDs TC-REG-01, TC-REG-02, ..., type, priority, tags, steps, expected result and whether to automate. It covers every acceptance criterion, every required field and validation rule, boundaries, roles and UI states, and lists open questions. No code is written in this step. A baseline (stage cases) is recorded.

Step 3: review the test cases (the most important human step)

Read every row. Fix expected results, remove noise, add what's missing, answer the open questions with the developer/PO. A wrong expected result caught here never becomes a wrong test. Edit the MD file directly or ask Claude to change it.

Step 4: automate

/qa-automate apps/shop/test-cases/web/registration.testcases.md

Claude then:

  1. opens the page in the MCP browser, logs in with the QA account of the right role, lists the real test IDs and triggers validation errors to read their exact texts;
  2. writes the model, page, fixture registration, data and spec, reusing what already exists;
  3. runs npx tsc --noEmit and the new spec, and fixes automation problems until the tests pass;
  4. if the app behaves differently from the test case, keeps the assertion and reports it as a suspected bug;
  5. runs coverage, records the baseline (stage automated) and reports back per test-case ID.

Step 5: review the generated code

Check it like a colleague's pull request: locators only in the model, one test per ID, expected texts match the test cases, no sleeps, no weakened checks, data cleaned up. Then commit.

Step 6: triage failures

/qa-fix apps/shop/tests/web/registration          # or a tag: /qa-fix @smoke   or empty: everything

Claude runs the tests, reads the failure details, reproduces each one in the browser and classifies it: automation issue (fixed in model/page/data), framework issue (fixed in src/ only if generic), application bug (assertion kept, knownBug(...) added with the Jira key you give it) or unclear requirement (question to you).

Step 7: check coverage

npm run coverage:tc                 # every test-case ID: automated / MISSING / planned / manual, and the % covered

Step 8: sign off

npm run req:baseline -- apps/shop/requirements/web/SCRUM-123-registration.md --stage signed-off --by "Your Name"

Only QA records signed-off, after the results are accepted. Attach the Allure report to the Jira story.

5.1 When the developer changes the module later

Every requirement has a baseline: the version QA last processed. When the developer updates the MD file:

npm run req:status                                  # all modules: stage, automation x/y, CHANGED flag
npm run req:diff -- apps/shop/requirements/web/SCRUM-123-registration.md
#   ## Fields
#     ~ CHANGED  Password: Error message: "Password is required" -> "Password must be at least 8 characters"
#     + ADDED    Remember me (Type: checkbox; ...)
/qa-update apps/shop/requirements/web/SCRUM-123-registration.md

/qa-update changes only what is affected: new cases get the next free IDs, changed cases keep their IDs, removed behaviour is retired with Automate: no (never deleted or renumbered). It updates the tests, runs them plus the module's smoke tests, and gives you a re-test list. Sign off again when done.

Don't edit by hand Never edit files in requirements/.baseline/ and never renumber test-case IDs: reports, coverage and history depend on them.

6. Working in sprints

A project is delivered in sprints, and each sprint has several user stories. Usually there is a web app, and sometimes a mobile app as well. This chapter shows how the per-module workflow from chapter 5 fits into that rhythm.

6.1 Who does what

WhoWhat they do with the framework
QAOwns the framework and every file in it: requirement files, test cases, code and reports.
DevelopersDon't use the framework. With every build they send one MD file per story in their own format, the build details and the credentials QA needs. The checklist to send them once is templates/dev-handover.md.

6.2 Starting a new web app

Do this once per project, before the first sprint. Chapter 7 explains each setting in more detail.

  1. Create the app folder: npm run new:app -- prj --platforms web,api (leave out api if there are no API tests). It creates apps/prj/ with requirements/, test-cases/, sprints/, the code folders, a starter app.config.ts, fixtures.ts and .env.
  2. Make it the active app: APP=prj in the root .env.
  3. Fill in app.config.ts: baseUrl (the QA URL), testIdAttribute (ask the developers: data-testid, data-test or data-qa), and auth.roles with a defaultRole.
  4. Fill in apps/prj/.env with the accounts the developers shared (USER_USERNAME, USER_PASSWORD, ...). For email OTPs, the MAIL_* settings, then npm run mail:check.
  5. Automate the login first, because every test starts logged in: requirement requirements/web/PRJ-001-login.md → /qa-testcases → review → /qa-automate. Ask Claude to wire the login steps into auth.login, then run npm run auth: every role must log in.
  6. Put the framework in Git and commit.
  7. Send the developers templates/dev-handover.md, so they know what to send with each build.
First sprint tips
  • The login tests are the first @smoke tests. Tag the main happy path of each new story @smoke so the smoke suite grows every sprint.
  • On machines with NODE_ENV=production, install with npm install --include=dev, or the Playwright packages are left out.
  • While working on one spec: npx playwright test <file> --project=web-chrome.

Testing days/qa-automate for each test-cases file. The MCP browser now finds the real locators in the build. /qa-fix for failures. Raise real bugs in Jira and add knownBug(...) to the test.
Bug-fix buildsNew developer MDs go in a new date folder. Merge again, then req:diff → /qa-update.
Sprint endnpm run test:regression (earlier sprints included), npm run coverage:tc, a clean req:status, and a signed-off baseline per story. Fill in the sign-off part of the sprint file.

6.5 Build day: save, merge, compare

  1. Save each developer MD unchanged in sprints/sprint-NN/from-dev/<YYYY-MM-DD>/ and add a row to the "Builds received" table of the sprint file. These copies are the record of what was delivered.
  2. Credentials: put them in apps/<app>/.env (6.6), then run npm run auth.
  3. Merge each developer MD into its requirement file. Ask Claude: 
    Merge the developer notes in apps/prj/sprints/sprint-03/from-dev/2026-10-15/PRJ-101-login.md into
apps/prj/requirements/web/PRJ-101-login.md. Keep the template structure, fill in the build details,
test IDs and exact messages they give, and add a Change log row "Merged dev notes, build 1.4.0".
List every point where the developer notes contradict what was there.
  4. Compare: 
    npm run req:status                                       # merged stories show CHANGED
npm run req:diff -- apps/prj/requirements/web/PRJ-101-login.md   # QA's expectation vs. the build
    Each difference is either accepted (then run /qa-update on the requirement, which updates only the affected test cases and tests) or questioned (ask the developer, note it in the sprint file, and raise a bug if the build is wrong).
Why QA drafts the requirement before the build The test cases are ready when the build arrives, so testing starts on day one. The diff also shows exactly where the developers built something different from the story, which would otherwise go unnoticed.

6.6 Credentials

  • Developers share credentials through the password manager or another secure channel, never inside the MD files.
  • QA stores them only in apps/<app>/.env (not committed). Requirement files and test code refer to the variable name (ADMIN_PASSWORD), never the value.
  • A new role: add it to auth.roles in app.config.ts and its variables to .env, then run npm run auth.
  • OTP or email verification: use the test inbox (MAIL_*, npm run mail:check) or a fixed QA-only code in OTP_CODE.

6.7 Web and mobile

The same story on web and mobile gets two requirement files (requirements/web/ and requirements/mobile/) and two test-cases files, because the screens, test IDs and builds differ. If the mobile app arrives in a later sprint, its file is added then and the web file is not touched.

7. Adding a new application

npm run new:app -- customer-portal --platforms web,mobile-web,android

This creates apps/customer-portal/ with the standard folders, a starter app.config.ts, fixtures.ts and .env.example. Then:

  1. app.config.ts: name, platforms, QA base URL, the test-ID attribute the developers use (data-testid, data-test, data-qa, ...), the login roles and the login steps.
  2. .env: copy .env.example, fill in accounts per role (the names you used in app.config.ts), API URL/token, mobile builds.
  3. Root .env: APP=customer-portal, or set it per command (section 10).
  4. Build the login page model and page first (with Claude: give it the login requirement), because auth.login uses it.
  5. Run npm run auth to check every role can log in, then continue with modules (section 5).
// apps/customer-portal/app.config.ts
export default defineApp({
  name: 'Customer Portal',
  platforms: ['web', 'mobile-web', 'android'],
  web: { baseUrl: 'https://qa.portal.example.com', testIdAttribute: 'data-testid' },
  auth: {
    defaultRole: 'customer',
    roles: {
      customer: { usernameEnv: 'CUSTOMER_USERNAME', passwordEnv: 'CUSTOMER_PASSWORD' },
      admin:    { usernameEnv: 'ADMIN_USERNAME',    passwordEnv: 'ADMIN_PASSWORD' },
    },
    login: async (page, credentials) => {
      const loginPage = new LoginPage(page);
      await loginPage.open();
      await loginPage.login(credentials);
      await new DashboardPage(page).expectLoaded();       // wait until really logged in
    },
  },
});

Apps without a login simply leave out auth.

9. Native mobile tests (Appium)

Optional. Until a mobile app is configured, mobile tests are skipped automatically, so the rest works without this.

9.1 Setup

npm i -g appium
appium driver install uiautomator2        # Android
appium driver install xcuitest            # iOS (macOS + Xcode only)
appium                                    # start the server (default http://127.0.0.1:4723), keep it running

Android needs Android Studio (SDK + an emulator) or a real device with USB debugging. In apps/<app>/.env set ANDROID_APP (path to the .apk) or ANDROID_APP_PACKAGE + ANDROID_APP_ACTIVITY for an installed app, and ANDROID_DEVICE (e.g. emulator-5554). iOS: IOS_APP or IOS_BUNDLE_ID, plus IOS_DEVICE. Mobile accounts go in MOBILE_USERNAME / MOBILE_PASSWORD (or as your app defines them).

9.2 Writing mobile tests

Same pattern as web: defineMobileFields models in models/mobile, screens extending BaseScreen in screens/, specs in tests/mobile. Actions: tap, type, setSwitch, choose, getText, isDisplayed, swipe, hideKeyboard, back, setValue, fillForm. Checks: visible, hidden, text, containsText. One Appium session per test; on failure a screenshot and the screen's XML source are attached.

Claude can't see native apps The MCP browser only works for web. For native screens, put the accessibility IDs in the module MD file (from the developers or Appium Inspector). /qa-automate asks for them if they are missing.

10.2 In CI

  • Set CI=true (most CI systems do): 2 retries, 2 workers, and test.only left in code fails the run.
  • Provide APP, TEST_ENV and every account/token as CI secrets (environment variables). They override the .env files, which are not in the repository.
  • Steps: npm ci → npx playwright install --with-deps chromium webkit → npx tsc --noEmit → npm test → npm run allure:generate and publish allure-report/.
  • npm run coverage:tc -- <app> --strict fails the build when a case marked Automate: yes has no test.
  • Keep allure-history.jsonl between runs (cache/artifact) to get trend charts.

11. Reports and failure triage

11.1 The Allure report

npm run report builds and opens it. What you get with no extra code in the specs:

  • A tree grouped Epic → Feature → Story → test (from storyInfo), with Jira links.
  • For every test: its test case (preconditions, steps, expected result) from the *.testcases.md file, severity from its priority, platform and role.
  • Readable steps (Fill "Username" with "standard_user", passwords masked), screenshot, video and trace on failure.
  • A Dashboard with status trends, severity and duration charts.

npm run report:html opens Playwright's own report, useful for the trace viewer (time-travel through each step).

11.2 Every failure comes with a cause and a bug report

The framework classifies each failure and the Categories tab sorts them:

CategoryTypical causesWho looks
Product bugsWrong text or value, wrong page/URL, element missing/disabled when it shouldn't beDevelopers
Automation issuesLocator not found or not unique, setup/configuration, error in test codeQA
Environment problemsServer unreachable, slow response, timeoutsDevOps / re-run
FlakyPassed only after a retryQA

Each failed test has a Bug report attachment: steps to reproduce with the real data, expected vs actual, environment, browser or device, page URL, browser console errors, failed API calls, and a text version to paste into Jira. The cause is a strong hint, not a verdict: QA (or /qa-fix) confirms it.

11.3 Known bugs

test('TC-REG-05 | Duplicate email is rejected', { tag: ['@regression', '@TC-REG-05'] }, async ({ registerPage }) => {
  knownBug('SCRUM-456', 'Duplicate email is accepted');      // first line of the test
  ...                                                         // assertions unchanged
});

The test stays green while the bug exists and is linked to it in the report. Once developers fix the bug, the test turns red ("passed unexpectedly"): that's the signal to remove the knownBug line.

11.4 Run history: every report is kept

The working folders (allure-results/, allure-report/, test-results/) are overwritten by each run. So that nothing is lost, every run also saves its own report permanently:

reports/
  index.html                                   list of every saved run (npm run reports)
  saucedemo/
    2026-10-05_17-47-38_qa_PASSED/
      report.html                              full Allure report of that run: one file, opens offline
      summary.json                             date, app, environment, projects, counts, command
    2026-10-06_09-12-03_staging_FAILED/
      ...
  • npm run reports opens the list: date, app, environment, status, passed/failed/flaky/skipped, duration, the command that was run, and an Open report link. Use the filter box to find a run by date, app or status.
  • Each report.html is self-contained (screenshots and failure details included). Copy it, attach it to Jira or email it.
  • The run is saved automatically at the end of npm test and every test:* command. The login refresh alone (npm run auth) is not saved.
  • Settings in the root .env: REPORT_KEEP_DAYS=30 deletes runs older than 30 days (default 0 keeps everything); REPORT_ARCHIVE=off stops saving, for example while re-running one test many times during debugging.
  • A report is about 4 MB, more when failures include videos. reports/ is not committed to git; back it up or move it to a shared drive if the team needs it.

12. Rules of the framework

These are also in CLAUDE.md, so Claude follows them. Reviewers check them on every change.

Do

  • Import test/expect from @apps/<app>/fixtures
  • Keep locators in models only; pages use act/verify
  • Derive data types from models: FormData<typeof XFields>
  • One test per test-case ID, title <ID> | <Title>, tags @smoke/@regression + @<ID>
  • storyInfo({...}) in beforeEach
  • Create data via api and register cleanup.add(...)
  • Read settings with getEnv/requireEnv
  • Run npx tsc --noEmit after every change
  • Put app-specific code in apps/<app>/

Don't

  • Import from @playwright/test in specs
  • Use waitForTimeout or any sleep
  • Write raw locators in pages, screens or specs
  • Weaken an assertion to match a bug: use knownBug
  • Renumber test-case IDs or delete retired cases
  • Edit requirements/.baseline/ by hand
  • Put app-specific code in src/ (change src/ only for generic improvements, and run every app's tests)
  • Print, commit or email .env files or saved logins

13. Working well with Claude

  • Start with the slash commands. They carry the whole procedure. Plain prompts are fine for questions and small changes.
  • Give file paths, not descriptions. /qa-automate apps/shop/test-cases/web/cart.testcases.md beats "automate the cart".
  • Good input, good output. Vague requirements produce vague tests. Fix the MD file rather than patching tests afterwards.
  • Review before you accept. Read test cases and code diffs. Claude asks before running commands or editing files; read what it asks.
  • Be specific when correcting. "TC-REG-04 expects the wrong text: the spec says 'Enter a valid email address'" is better than "fix the test".
  • One module per conversation. Start a new conversation for a new module; long conversations get summarised and lose detail.
  • Tell it about bugs. When you've raised a Jira bug, give Claude the key so it can add knownBug.
  • Teach the rules once. If you keep giving the same correction, add it to CLAUDE.md (team-wide, via a PR) so every conversation follows it.
  • Secrets stay local. Claude reads test accounts from .env to log in but is instructed never to print them. Never paste real production credentials into a conversation.
