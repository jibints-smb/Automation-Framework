The one-sentence version

For every module, the developer hands QA one Markdown file that lists every field, rule, message and test ID (Section 3 and the template in Appendix A). QA turns it into reviewed test cases, Claude turns those into automated tests, and the results appear in the Allure report linked to the Jira story.

1. Purpose and who does what

This guide describes how every module of our web and mobile applications is tested with the shared automation framework, and what information has to be agreed before testing starts. Automation quality depends on the quality of its input: most flaky or wrong tests come from vague requirements ("show an error") or from UI elements that can't be located reliably. A complete module MD file solves both.

1.1 Roles

RoleResponsibilities
DeveloperWrites or completes the module MD file (fields, rules, exact messages, test IDs, APIs, test data). Adds data-testid / accessibility IDs in the code. Deploys the build to the QA environment. Fixes confirmed bugs.
Product owner / BAOwns the Jira story and acceptance criteria. Answers open questions about business rules.

Claude (AI assistant)Drafts test cases from the MD file, explores the app through the Playwright MCP browser, writes the model, page, data and spec code, runs tests and proposes fixes. Its output is always reviewed by QA.

1.3 One framework, many applications

Every project uses the same framework. A new application is added with npm run new:app -- <name> --platforms web,android, which creates apps/<name>/. The developer and QA then fill in app.config.ts (QA URL, test-ID attribute, user roles and how to log in) and the app's .env (test accounts, app builds). The active application is chosen with the APP setting. Improvements to the framework reach every project at once.

Step 1: Developer writes the module MD file

As soon as the story is in development, the developer copies templates/requirement.md to apps/<app>/requirements/<JIRA-KEY>-<module>.md and fills it in (Section 3 explains every part). Free-form notes are accepted, but the information in Section 3 must be in there.

Output: module MD file committed or shared with QA.   Done when: it passes the Definition of Ready (Section 5).

Step 2: QA checks the Definition of Ready

QA reads the file against the checklist in Section 5. Missing exact messages, missing test IDs or unclear rules go back to the developer as comments on the Jira story. Automation does not start on an incomplete spec: guessing produces tests that check the wrong thing.

Step 3: Generate test cases

In VS Code, QA runs /qa-testcases apps/shop/requirements/SCRUM-123-registration.md. Claude reads the file, optionally opens the page in a browser to confirm fields and messages, and writes apps/shop/test-cases/registration.testcases.md containing:

  • at least one positive case for every acceptance criterion;
  • negative cases for every required field and every validation rule;
  • boundary cases for lengths and ranges (min−1, min, max, max+1);
  • cases for business rules, roles/permissions and UI states (empty, disabled, error);
  • IDs TC-<MODULE>-NN, tags @smoke (main happy path) or @regression, and whether each case can be automated.

Claude also lists gaps and questions, for example an error message that is not specified.

Step 4: Review the test cases

QA reviews the test-cases file and shares it with the developer and PO (in the PR or the Jira story). This is the cheapest place to catch misunderstandings: a wrong expected result fixed here never becomes a wrong test.

Step 5: Automate

QA runs /qa-automate apps/shop/test-cases/registration.testcases.md. Claude:

  1. opens the application through the Playwright MCP browser and confirms locators and message texts (web);
  2. creates the field model, page/screen object, test data and spec (Section 7);
  3. type-checks and runs the new tests, fixing automation problems until they pass;
  4. reports any test that fails because the application behaves differently from the spec (a possible bug).

QA reviews the generated code like any pull request.

Step 6: Run on every platform

Web specs run on desktop Chrome and on mobile emulation (Pixel 7, iPhone 15). Native app specs run on Android and iOS through Appium. The same tests run in CI on every deployment to the QA environment.

Step 7: Triage failures

QA runs /qa-fix for failing tests. Each failure is classified as an automation issue (fixed in the framework), an application bug (Jira bug raised, test marked as expected-to-fail with the bug key), or an unclear requirement (question to PO). See Section 9.

Step 8: Sign-off

The module is signed off when every automatable test case passes (or is linked to an accepted, open bug) on all target platforms. The Allure report link is attached to the Jira story.

Typical timeline for one module

Spec ready with the code → test cases same day → review within 1 day → automation and first run within 1–2 days → regression on every later build at no extra cost.

3. The module MD file: what developers must provide

One file per module (or per story that changes a module). Use the template in templates/requirement.md (reproduced in Appendix A). Sections marked required must be complete before QA starts. The table below explains what each section is used for, so it's clear why the detail matters.

SectionWhat to writeHow automation uses it
1. Overview required Jira key, epic, module, platform, QA URL/path, build or app version, feature flag, priority, names. Allure grouping (Epic → Feature → Story), Jira link in the report, which test projects run, the base URL.
2. User story required As a … I want … so that … Story label in the report; context for test-case generation.
3. Acceptance criteria required Numbered (AC1, AC2…), testable, Given/When/Then, exact expected texts in quotes. Each AC becomes at least one test case; traceability AC → test ID.
4. Entry point & preconditions required URL or menu path, roles that can access it, data that must exist first. Page path, which login session to use, setup steps.
5. Fields required Every input, dropdown, checkbox, button and label with type, test ID, required, default, rules, dependencies and exact error message. Becomes the field model directly; drives negative and boundary cases; error texts become assertions.
6. Actions & outcomes required Each button/link: when it is enabled, what happens on success (navigate, toast, close dialog) and on failure. Page methods (submit(), cancel()) and their expected results.
7. Messages required Every toast, banner, dialog and empty state, with its test ID and exact text including punctuation. The Messages constant in the model; text assertions.
8. Business rules Calculations, limits, role permissions, conditional fields, uniqueness (e.g. "email must be unique"). Dedicated rule test cases; data-driven tests for calculations.
9. UI states Loading, empty, server-error, disabled/read-only behaviour. State tests, often using API mocking.
10. APIs Endpoints the screen calls, with method, purpose, success and error codes. Fast test setup and cleanup via API; mocking error states; checking that the right request is sent.
11. Test data & accounts required Accounts per role (password as an .env variable name, never the value), seed data, cleanup method, OTP/captcha/email bypass. Roles in app.config.ts, accounts in the app .env, data files; API cleanup keeps tests repeatable.
12. Mobile only APK/IPA link, package/bundle ID, launch activity, OS versions, permissions, deep links. Appium capabilities in .env; deep links skip slow navigation.
13. Out of scope / known issues What is not delivered yet; known bugs with Jira keys. Prevents false failures; known bugs become expected-to-fail tests.
14. Change log Date, what changed, who. Tells QA which test cases and models to update.

4. Test ID contract (web and mobile)

Automated tests find elements by a dedicated, stable attribute rather than CSS classes, XPath or visible text, which change with styling, refactoring and translations. Adding test IDs is a small development task that makes automation much more stable. Every element listed in the fields, actions and messages tables needs one.

4.1 Naming convention

<module>-<element>-<kind>            kebab-case, lower case, English, no spaces

register-email-input        register-submit-button      register-email-error
register-country-select     register-terms-checkbox     register-success-toast
orders-row-<orderId>        orders-row-<orderId>-delete-button     (lists: append the record's stable id)
Kind suffixUse for
-inputtext, email, password, number, date, textarea
-selectdropdowns / pickers
-checkbox, -radio, -switchtoggles (for radio groups put the ID on the group, and give each option a unique ID or label)
-button, -linkactions and navigation
-errorthe inline validation message of a field
-toast, -banner, -dialogfeedback messages and modals
-title, -label, -valueread-only text that tests check
-row, -card, -listrepeated items and their container

4.2 How to add them, per technology

TechnologyCode
HTML / React / Angular / Vue<input data-testid="register-email-input" />
React Native<TextInput testID="register-email-input" accessibilityLabel="register-email-input" />
FlutterSemantics(identifier: 'register-email-input', child: ...) or Key('register-email-input') with the Appium Flutter driver
Android (XML / Compose)android:id="@+id/register_email_input" and/or android:contentDescription; Compose: Modifier.testTag("register-email-input") with testTagsAsResourceId = true
iOS (UIKit / SwiftUI)view.accessibilityIdentifier = "register-email-input"; SwiftUI: .accessibilityIdentifier("register-email-input")

4.3 Rules

  • Stable: never generated (no input-4821, no hashed class names) and not changed during refactoring.
  • Unique on the screen. In lists, append the record's business ID, not its position.
  • Not translated: test IDs stay English when the UI language changes.
  • Present in QA/staging builds. They may be stripped from production if required, but never from test builds.
  • On mobile, use the same IDs on Android and iOS when possible, so one model serves both platforms.
  • The attribute name (data-testid, data-test, data-qa) is configurable per application (testIdAttribute in the app's app.config.ts); pick one per application and use it everywhere.
No test IDs yet?

The framework can fall back to accessible roles and labels (for example "the button named Register"), which Claude finds through the Playwright MCP. This works, but breaks when texts change or the app is translated. Treat missing test IDs as technical debt to be fixed in the next sprint.

5. Definition of Ready checklist

QA checks a module MD file against this list before generating test cases. Every unchecked item goes back to the developer or PO as a Jira comment.

Scope and access

  • Jira key, epic, module and platform(s) filled in
  • QA environment URL / app build available and working
  • Feature flag named, with how to switch it on
  • Entry point (URL, menu path or deep link) given
  • Roles that can and cannot access the module listed

Behaviour

  • Acceptance criteria numbered and testable
  • Every button has success and failure outcomes
  • Business rules have concrete numbers and limits
  • Conditional fields and their trigger values described
  • Loading, empty and error states described

Fields and messages

  • Every field has type, required flag and rules
  • Lengths, ranges and formats are specific numbers or patterns
  • Dropdown / radio options listed in display order
  • Every validation rule has its own exact error text
  • Every toast, banner and dialog text is exact

Testability

  • Every element in the tables has a test ID (Section 4)
  • Test accounts exist for every role (passwords via .env)
  • Way to create and clean up test data (API or script)
  • OTP, captcha and email have a test bypass
  • Mobile: APK/IPA, package/bundle ID and devices given

7.1 The four layers

// 1. MODEL: the fields table, as data
export const RegistrationFields = defineWebFields({
  email: {
    label: 'Email', type: 'email', locator: { testId: 'register-email-input' },
    rules: { required: true, maxLength: 100,
             messages: { required: 'Email is required', pattern: 'Enter a valid email address' } },
  },
  terms:  { label: 'I accept the terms', type: 'checkbox', locator: { testId: 'register-terms-checkbox' } },
  submit: { label: 'Create account',     type: 'button',   locator: { testId: 'register-submit-button' } },
  // ... one entry per row
});
export type RegistrationData = FormData<typeof RegistrationFields>;   // typed automatically

// 2. PAGE: business actions, no locators
export class RegistrationPage extends BasePage {
  readonly path = '/register';
  readonly fields = RegistrationFields;
  async register(data: RegistrationData) {
    await this.act.fillForm(this.fields, data);      // fills each field according to its type
    await this.act.click(this.fields.submit);
  }
}

// 3. DATA: typed by the model
export const validCustomer: RegistrationData = { firstName: 'Asha', email: uniqueEmail(), terms: true, /* ... */ };

// 4. SPEC: reads like the test case
test('TC-REG-01 | Valid registration shows welcome toast and opens /account',
  { tag: ['@smoke', '@TC-REG-01'] }, async ({ registrationPage }) => {
    await registrationPage.register(validCustomer);
    await registrationPage.expectWelcome(validCustomer.firstName!);
  });

7.2 What appears in the report

Every action is a readable step, so a failed test can be understood without opening the code:

TC-REG-01 | Valid registration shows welcome toast and opens /account
  Open "/register"
  Fill "First name" with "Asha"
  Fill "Email" with "qa.lx3k9a@example.com"
  Fill "Password" with "********"          <- passwords are always masked
  Check "I accept the terms"
  Click "Create account"
  Verify "Welcome toast" has text "Welcome, Asha!"

7.3 Mobile modules

Native screens follow the same pattern: defineMobileFields, a screen object extending BaseScreen, and this.act.tap / type / fillForm / swipe. If Android and iOS use different IDs, a field can declare both: locator: { android: { id: '...' }, ios: { accessibilityId: '...' } }. The Playwright MCP cannot drive native apps, so mobile locators come from the MD file (Section 12 and the test ID column) or from Appium Inspector.

8.2 Reading the report

Results tree

Results grouped by Epic → Feature → Story, matching Jira. Use it for module sign-off. Role logins appear under Test setup.

Test detail

The description shows the test case (preconditions, steps, expected result) from the test-cases file, then the readable steps, Jira link, severity and tags.

Categories tab

Failures sorted by likely cause: Product bugs (developers start here), Automation issues (QA) and Environment problems.

History, dashboard

Run history shows flaky tests and regressions. The report's start page also links a Dashboard with charts and trends.

What a failed test shows

Every failed test opens with a summary (likely cause, the step that failed, expected vs actual) and has a Bug report attachment, generated automatically for every application:

  • Expected vs Actual: what the test checked, the test case's expected result and what the app showed;
  • Steps to reproduce: every executed step with the real data (passwords masked) and the failing step marked;
  • Details: Jira story and test case, severity, environment and URL, browser/version or device, user role, page URL at failure, attempt;
  • Browser console errors and failed network requests (4xx/5xx) captured during the test;
  • the error and Playwright call log, and a Copy for Jira text block;
  • next to it: screenshot, video and trace (web), or screenshot and page source (mobile).
The likely cause is a first guess

It is based on the failing step and error (wrong text, wrong page, element not found, server unreachable). When the test checked a different text than the test case specifies, the failure is marked as an automation issue, not a product bug. QA confirms the cause before a Jira bug is raised (Section 9).

8.3 Severity

The story's priority in the MD file becomes the Allure severity: blocker (release stopper), critical (core flow broken), normal, minor, trivial. A release needs zero failing blocker and critical tests.

9. Failure triage and bug reporting

Each failing test is classified before anything is changed. /qa-fix helps: Claude re-runs the test, reproduces it in the browser and proposes a classification, and QA confirms it.

ClassificationTypical signsAction
Automation issueElement not found after a UI change, timing, expired test data, environment down Fix the model locator, data or setup. Never weaken an assertion to make a test pass.
Application bugBehaviour differs from the MD file / test case: wrong message, wrong navigation, data not saved Raise a Jira bug (copy the Copy for Jira text from the Bug report). Add knownBug('SCRUM-456', 'summary') as the first line of the test: it stays green while the bug exists, links the bug in the report, and turns red once the bug is fixed, so QA removes the line.
Spec changedDeveloper changed behaviour on purpose, but the MD file wasn't updated Developer updates the MD file and change log; QA updates test cases and the model.
Unclear requirementBoth behaviours seem reasonable Ask the PO; the test stays as it is until answered.

9.1 Bug report contents

  • Title: [Registration] Duplicate email accepted (TC-REG-02)
  • Story / test case: SCRUM-123, TC-REG-02
  • Environment: QA, web 4.12.0, Chrome desktop (and others where it reproduces)
  • Steps: from the Bug report's Steps to reproduce (or its Copy for Jira block)
  • Expected: from the MD file, with the exact text. Actual: what happened.
  • Evidence: Allure report link, screenshot, trace or video

10. When a module changes after testing

Modules change after QA has tested them: a bug fix adds a field, a validation message is reworded, a new acceptance criterion appears. The framework records which version of each module MD file QA last processed (the baseline), so changes are found automatically. Nobody has to compare files by eye or remember what was tested.

10.3 What /qa-update does with the changes

Change in the MDEffect on test cases and automation
Field / AC / rule / message addedNew test cases with the next free IDs; model, page, data and specs extended
Rule or exact text changedAffected test cases updated, same IDs; assertions updated
Behaviour removedTest cases retired (Automate: no, kept for history); their tests removed
Priority changedSeverity and tags updated

It also re-runs the module's smoke tests (a fix can break the happy path), adds an entry to the test-cases file's Change history, records the new baseline as Automated, and gives QA a re-test list. QA re-tests and signs off.

For developers
  • Always edit the same module MD file. Don't create a new copy per iteration, or the history is lost.
  • Rows are matched by their first column (field name, action, message key). A renamed field therefore shows as removed + added; write the rename in the change log ("Mobile" renamed to "Phone number") so QA keeps the same test cases.
  • Add a change-log line (section 14) with the Jira bug key, e.g. 2026-10-09 | Password min length 8 (SCRUM-456) | A. Dev.

Baselines are stored in apps/<app>/requirements/.baseline/ and are committed with the repository, so the whole team (and CI) sees the same status.

11. Things that block automation, and how to avoid them

ProblemEffect on testsDeveloper-side solution
No test IDs, or generated IDsBrittle locators that break on every UI changeAdd test IDs per Section 4
Vague or missing messagesTests can only check "some error", so real bugs slip throughExact text per rule in the MD file
OTP / SMS / captchaCannot be automated reliablyFixed OTP or bypass in QA env, or a test API that returns the OTP; captcha disabled for test accounts
Email verification linksTests stuck waiting for an inboxTest inbox API (e.g. Mailpit/Mailhog) or an endpoint that returns or verifies the link
Shared or changing test dataTests pass alone and fail togetherDedicated accounts per role; create and delete data via API
No cleanup endpointDatabase fills up; unique-value rules start failingQA-only cleanup API or nightly reset script
Animations, long loadersSlow, flaky testsLoading indicators with test IDs; reduced-motion respected
Third-party widgets (payments, maps) in iframesSlow, unstable, may hit real servicesSandbox mode and documented test cards; feature flag to stub
Behaviour depends on date/time or locationTests fail on certain days or machinesDocument the rule; allow time and locale override in QA env
Mobile: no debuggable buildAppium cannot inspect the appProvide QA builds (debug/ad-hoc signed) with accessibility IDs
Spec not updated after a changeTests fail on correct behaviourUpdate the MD file and change log in the same PR as the code
Golden rule for developers

If a person needs to ask you a question to know whether the screen behaves correctly, the answer belongs in the module MD file.

Appendix B: Glossary and commands

TermMeaning
Module MD fileThe Markdown specification of one module or story, written by the developer (Section 3).
Test-cases fileReviewed list of test cases derived from the module MD file; one row = one automated test.
Field modelCode description of a page's fields (label, type, locator, rules); the only place locators live.
Page / screen objectClass with business actions for one web page or mobile screen (register(), expectError()).
Test IDStable attribute used to find an element: data-testid on web, accessibility ID on mobile.
PlaywrightBrowser automation framework used for web and mobile-web tests, and as the test runner for everything.
AppiumAutomation server for native Android/iOS apps, driven through WebdriverIO.
MCP / Playwright MCPLets Claude control a real browser to explore pages, find locators and confirm behaviour.
AllureTest report grouped by Epic/Feature/Story, with steps, attachments, Jira links and history.
Smoke / regressionSmoke: a few critical happy paths run on every build. Regression: the full set.
Definition of ReadyChecklist a module MD file must pass before testing starts (Section 5).
